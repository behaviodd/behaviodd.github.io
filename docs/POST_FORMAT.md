# 작업기 포스트 양식

바이브 코딩 시리즈(작업기) 글은 아래 양식으로 통일한다.
기준 구현: `_posts/2026-05-16-simple-event-winner.md`

## 원칙

스펙 나열이 아니라 **판단의 기록**을 쓴다. "무엇을 만들었다"보다 "왜 그렇게 정했다"에 지면을 쓰고,
기능 목록·스택·데이터 모델처럼 검증 가능한 사실은 접힘 영역으로 내린다.

## 골격

```markdown
---
title: {서비스명} 작업기          # '구축기' 아님. 본문에 H1을 다시 쓰지 않는다
date: YYYY-MM-DD                  # 기존 발행일 유지
layout: post
---

> 바이브 코딩 시리즈 · 5편 중 N편

{2~3줄 리드. 무엇인지 한 문장 + URL 공개 여부}

<!-- 이미지 자리 ①: 히어로 -->

---

## 왜 만들었나
## 무엇을 만들었나
## 판단이 필요했던 순간들
## AI가 한 것 / 내가 한 것
## 회고

---

<details markdown="1">
<summary><b>기술 상세</b> — 스택 · 아키텍처 · 데이터 모델 · 프로젝트 구조</summary>
...
</details>
```

## 섹션별 규칙

| 섹션 | 분량 | 내용 |
| --- | --- | --- |
| 왜 만들었나 | 2~3문단 | 원래 어떻게 하고 있었는지 → 그 방식의 **구조적 결함** 한 가지 |
| 무엇을 만들었나 | 4개 이내 | `**굵은 리드문.**` + 1~2문장. 기능 목록이 아니라 사용자가 얻는 것 |
| 판단이 필요했던 순간들 | 3~5개 | `### N. {결정}` + **2문단**. 1문단=상황/딜레마, 2문단=선택과 근거 |
| AI가 한 것 / 내가 한 것 | 4문단 | 잘 위임된 것 / 넘길 수 없었던 것 / 그래서 무엇이 바뀌었나 |
| 회고 | 각 3~4개 | `### 잘된 점` `### 개선할 점`. 한 항목 1~2문장 |

## 세부 규약

- **제목**: front matter `title`만 사용. 본문 H1 금지 (`post.html`이 이미 출력 → 중복)
- **시리즈 표기**: `> 바이브 코딩 시리즈 · 5편 중 N편`
  1. Matome Keyword / 2. K-POP Digging Club / 3. Luckydraw Maker / 4. Review MVP / 5. Simple Event Winner
  ※ 번호는 **최초 발행 순서로 고정**한다. 글 내용이 발행일 이후까지 확장돼 `date`를 갱신해도
    번호는 바꾸지 않는다(목록 정렬 순서와 시리즈 번호는 어긋날 수 있다).
  ※ Design System 작업기는 시리즈 제외
- **발행일**: 기존 발행일 유지가 기본. 단 글이 다루는 사건이 발행일 이후까지 이어지면
  마지막 작업 시점으로 `date`와 파일명을 갱신한다(permalink는 slug 기준이라 URL은 불변).
- **접힘 영역**: `<details markdown="1">` 필수 (`markdown="1"` 없으면 kramdown이 내부를 렌더하지 않음).
  스타일은 `_layouts/default.html`의 `.prose details` / `.prose summary` — `[+]`/`[-]` 마커
- **이미지**: 확보 전에는 HTML 주석으로 자리·요구사항·권장 경로를 남긴다.
  경로 규칙 `assets/images/{slug}/{name}.{ext}`
- **추정으로 쓴 문장**: 삭제하지 말고 위에 `<!-- 확인 필요: ... -->` 주석
- **분량 기준**: 접힘 위 본문 2,000~2,500자. 넘으면 판단 항목 수를 줄인다
- **문체**: 존댓말. 수식어·부연 최소화. 같은 일화를 두 섹션에서 반복하지 않는다
