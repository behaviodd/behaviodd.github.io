## 왜 만들었나

<!-- 확인 필요: 아래 문단은 추정. 실제 계기와 다르면 수정할 것 -->

K-POP을 오래 들으면 추천이 점점 좁아집니다. 스트리밍 서비스의 추천은 "이 곡을 들은 사람이 또 들은 곡"을 주는데, K-POP을 들은 사람은 대체로 K-POP을 또 듣기 때문입니다. 취향이 넓어지는 게 아니라 벽이 두꺼워집니다.

그런데 내가 그 곡에서 좋아한 건 "K-POP이라서"가 아니라 특정한 질감이었을 겁니다. 그 질감을 공유하는 곡이 노르웨이나 브라질에도 분명히 있을 텐데, 어떤 플랫폼도 거기까지 데려다주지 않습니다.

그래서 **좋아하는 곡의 음악적 DNA만 뽑아내고, 원래 장르는 결과에서 빼버리는** 도구를 만들었습니다.

---

## 무엇을 만들었나

**트랙 링크 하나면 됩니다.** Spotify나 Apple Music URL을 넣으면 태그·청취 패턴·템포를 분석해 유사 곡을 찾습니다.

**K-POP은 결과에서 제외합니다.** 3단계로 걸러내서, 익숙한 곡이 섞여 들어오지 않게 합니다.

**다섯 갈래로 동시에 뒤집니다.** Last.fm·Deezer·ListenBrainz를 서로 다른 방식으로 병렬 탐색해 한 플랫폼의 추천 편향을 상쇄합니다.

**들어보고 담을 수 있습니다.** 30초 프리뷰로 확인하고, 마음에 든 곡만 골라 Spotify 플레이리스트로 만듭니다.

---

## 판단이 필요했던 순간들

### 1. K-POP 도구에서 K-POP을 뺀 것

이름이 K-POP Digging Club인데 결과에는 K-POP이 한 곡도 나오지 않습니다. 처음엔 이게 맞나 싶었지만, 섞이면 도구의 존재 이유가 사라집니다. 아는 곡이 한 곡이라도 보이면 사람은 거기부터 클릭하니까요.

거르는 방법은 세 겹입니다. Last.fm의 k-pop 태그 상위 아티스트 500명 블록리스트, 아티스트명의 한글 감지, 곡 태그 키워드 필터. 이 중 **한글 감지는 명백히 거친 규칙**입니다. 한국 아티스트의 비K-POP 곡까지 같이 걸러지니까요. 그래도 남겨뒀습니다. 이 도구에서 오탐(놓치는 좋은 곡)의 비용은 낮고, 미탐(익숙한 곡이 섞임)의 비용은 도구 전체를 무의미하게 만듭니다.

### 2. 인기순이 아니라 '얼마나 깊게 들었나'로 정렬한 것

유사도 점수를 매길 때 제일 쉬운 축은 인기도입니다. 재생수가 많을수록 좋은 곡이라고 치는 것이죠. 그러면 이미 아는 곡이 위로 올라옵니다.

그래서 배점 최고점(23점)을 **Digging Index**에 줬습니다. 재생수를 리스너 수로 나눈 값 — 즉 *한 사람이 몇 번이나 다시 들었는가* 에 희소성 보너스를 얹은 지표입니다. 100만 명이 한 번씩 들은 곡보다 1만 명이 스무 번씩 들은 곡이 위로 옵니다. "숨겨진 보석"이라는 말을 점수로 옮기면 결국 이 비율입니다.

### 3. 데이터가 없는 곡에 0점을 주지 않은 것

BPM이나 오디오 피처가 없는 곡이 많습니다. 처음엔 없으면 해당 항목 0점으로 처리했는데, 그러면 **데이터가 있는 곡이 구조적으로 유리해집니다.** 음악이 좋아서가 아니라 Deezer에 메타데이터가 있어서 순위가 오르는 겁니다.

고정 보상점을 주는 방법도 있지만 그건 또 다른 임의값입니다. 대신 누락된 항목을 빼고 **나머지 배점을 비례 재정규화**했습니다. 어떤 조합이 빠지든 이론적 최대점은 항상 100점입니다. 덕분에 데이터가 부실한 무명 곡과 잘 정리된 곡이 같은 자로 비교됩니다.

### 4. 실패를 숨기지 않고 화면에 띄운 것

남의 API에만 의존하는 도구라 일곱 갈래 중 하나쯤은 늘 죽어 있습니다. 흔한 선택은 조용히 넘어가는 것입니다. 결과는 어차피 나오니까요.

그렇게 하지 않고 결과 화면 위에 `●●●○●●● 6/7 sources`를 띄웠습니다. 같은 30곡이라도 일곱 갈래에서 뽑은 30곡과 네 갈래에서 뽑은 30곡은 신뢰도가 다른데, **그 차이를 아는 쪽은 도구지 사용자가 아닙니다.** 알려주고 판단은 넘기는 게 맞다고 봤습니다.

### 5. 내 키는 감추고, 남의 계정은 만지지 않은 것

정적 사이트라 서버가 없습니다. 그런데 Last.fm API 키를 브라우저 코드에 그냥 둘 수는 없어서 Cloudflare Worker 하나를 프록시로 세웠습니다. 키 보호와 CORS 우회, 엔드포인트별 캐시(5분~7일)를 여기서 처리합니다.

반대로 **Spotify 플레이리스트 생성은 프록시를 거치지 않습니다.** PKCE OAuth로 브라우저가 Spotify와 직접 이야기합니다. 내 API 키는 감춰야 하지만, 사용자의 계정 토큰은 내 서버가 아예 만지지 않는 편이 낫기 때문입니다. 감출 것과 손대지 말 것은 다른 문제입니다.

---

## AI가 한 것 / 내가 한 것

**AI가 잘한 것.** TF-IDF 태그 유사도, 하모닉 BPM 매칭(half/double tempo까지), 일곱 개 외부 API 클라이언트, 캐시 TTL 설계, 비례 재정규화 구현. 명세가 서면 정확히 나왔고, 특히 재정규화처럼 "말로는 간단한데 계산이 성가신" 부분에서 시간을 크게 벌었습니다.

**넘길 수 없었던 것.** 배점표입니다. Digging Index 23점, Vibe Match 22점, BPM 10점 — 이 숫자에는 정답이 없습니다. "좋은 추천"이 무엇인지 정의하는 일이고, 정의를 바꾸면 결과가 통째로 바뀝니다. 한글 감지를 남겨둘지도 마찬가지였습니다. AI는 오탐률을 계산해줄 수 있지만, 오탐과 미탐 중 어느 쪽이 이 도구에서 더 치명적인지는 만든 사람이 정합니다.

결국 이 프로젝트에서 제가 한 일의 대부분은 **숫자를 고르고, 고른 이유를 설명할 수 있게 만드는 것**이었습니다.

## 회고

### 잘된 점

- **비례 재정규화.** 데이터 유무가 순위에 개입하지 않게 만든 것이 추천 품질에 가장 크게 기여했습니다.
- **프록시 경계.** 내 키는 Worker 뒤로, 사용자 토큰은 브라우저에서 직접. 서버 없이도 선이 명확합니다.
- **로그인 없는 취향 학습.** localStorage에 7일 반감기로 쌓으니 가입 절차 없이 두 번째 방문부터 결과가 달라집니다.

### 개선할 점

- 취향 프로필이 기기 간에 동기화되지 않습니다. 로그인을 안 받은 대가입니다.
- 한글 감지 오탐 — 한국 아티스트의 비K-POP 곡이 걸러집니다. 아티스트 단위 예외 목록이 필요합니다.
- Apple Music은 입력만 되고 플레이리스트 생성은 안 됩니다.
- Last.fm 태그는 사용자 입력이라 노이즈가 섞입니다. 비음악적 태그 40개를 막아뒀지만 충분하지 않습니다.
- `docs/KPOP_DIGGING_CLUB.md`가 실제 구현과 어긋나 있습니다(옛 배점표). 문서와 코드 중 하나는 항상 뒤처지는데, 이 경우엔 문서였습니다.

## K-POP 3단계 필터링

1. **아티스트 블록리스트** — Last.fm의 k-pop / kpop / korean pop 태그 상위 ~500명
2. **한글 감지** — 아티스트명에 `가-힣`, `ㄱ-ㅎ` 포함 시 제외
3. **태그 필터** — 곡 태그에 K-POP 관련 키워드 포함 시 제외

## 아키텍처

```
[Browser]  digging.html · 인라인 JS
     │
     ├─▶ [Cloudflare Worker]  키 보호 · CORS · 캐시
     │        └─▶ Spotify / Last.fm / Deezer / MusicBrainz / ListenBrainz
     │
     ├─▶ [iTunes API]   JSONP 직결 — 메타데이터 + 프리뷰
     │
     └─▶ [Spotify Auth] PKCE 직결 — 플레이리스트 생성
```

## 제한사항

- 프리뷰는 30초. 일부 국가에서는 제공되지 않습니다
- Last.fm 태그는 사용자 입력이라 노이즈가 있습니다
- Apple Music은 입력(메타데이터 조회)만 지원. 플레이리스트 생성은 Spotify만
- 취향 프로필은 localStorage 저장이라 기기 간 동기화되지 않습니다
- Track Features가 레이트 리밋에 걸리면 `(audio features limited)` 표시가 붙습니다
