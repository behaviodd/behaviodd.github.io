## 왜 만들었나

당첨자 선정은 원래 엑셀 수작업이었습니다. 한국 어드민 파일과 중국 Weidian 파일을 각각 열어 응모권별로 정렬하고, 중복 응모를 눈으로 찾아 합치고, 발표용으로 이름을 하나씩 별표 처리하는 일입니다.

문제는 **틀려도 티가 안 난다**는 것이었습니다. 정렬이 한 번 어긋나거나 중복 한 건을 놓쳐도 화면은 똑같이 멀쩡해 보입니다. 되돌릴 수 없는 작업인데 검증 수단이 사람의 주의력밖에 없었습니다.

요구사항의 대부분이 "이 경우엔 누구를 먼저 올릴 것인가" 같은 **운영 정책 판단**이었습니다. 명세로 옮겨 전달하고 확인받는 것보다 직접 만들어 보여주는 편이 빨라 보였습니다.

## 무엇을 만들었나

**한·중 파일을 한 번에 처리합니다.** 두 엑셀을 함께 올리면 응모권 단위로 통합되고, 여러 시트로 쪼개진 파일은 주문번호로 자동 병합합니다.

**중복 응모를 합칩니다.** 무엇을 기준으로 "같은 사람"으로 볼지는 운영자가 직접 켜고 끕니다.

**결과를 두 벌로 내려받습니다.** 검증용(마스킹 없음)과 발표용(마스킹 적용)이 분리돼 있고, 발표용 이미지는 4언어로 나옵니다.

**서버에 아무것도 보내지 않습니다.** 개인정보가 브라우저 밖으로 나가지 않습니다.

## 판단이 필요했던 순간들

### 1. 개인정보를 서버에 보내지 않기로 한 것

파일을 서버에 올리는 순간 이 도구는 개인정보를 **저장하는** 시스템이 됩니다. 보관 기간, 접근 권한, 파기 절차가 따라붙습니다. 그래서 파싱부터 다운로드까지 전부 브라우저 안에서 처리했습니다. 새로고침하면 데이터가 사라집니다.

비용은 번들 크기였습니다. 엑셀 서식을 유지하려면 `xlsx-js-style`(1.3MB+)을 통째로 실어야 했으니까요. 주 1~2회 쓰는 도구라, 첫 로딩 몇 초와 "이 도구는 아무것도 저장하지 않는다"는 한 문장을 맞바꿨습니다. 운영팀이 가장 좋아한 것도 그 문장이었습니다.

### 2. 한국과 중국의 공정성 규칙을 하나로 합친 것

처음엔 한국이 응모권 수량, 중국이 결제금액 기준이었습니다. 한·중 통합 dedup을 넣으면서 문제가 됐습니다. 양쪽에서 응모한 사람을 합산하면 **어느 규칙을 적용할지 정할 방법이 없었습니다.**

그래서 하나로 통일했습니다.

> 응모권 수량 내림차순 → 결제금액 내림차순 → 주문일시 오름차순 → 시드 기반 랜덤

주문일시를 오름차순으로 둔 건 의도적입니다. 조건이 같다면 먼저 응모한 사람이 앞에 오는 게 설명 가능한 공정성이라고 봤습니다. 기존 "엑셀 원본 행 순서" fallback은 폐기했습니다. 그건 우연이지 규칙이 아니니까요.

### 3. 합산 내역을 화면에만 넣은 것

"한 사람이 어떤 주문들로 합산됐는지 보고 싶다"는 요청이 왔습니다. 자연스러운 구현은 다운로드 시트에 열을 추가하는 것이었지만, 넣지 않았습니다.

결과 화면은 발표 직전에 검증하는 자리라 합산 근거가 필요합니다. 반면 다운로드 시트는 정산·외부 공유용 문서고, 거기서 "이 사람은 3건이 합쳐졌음"은 읽는 사람이 판단할 일 없는 노이즈입니다. 그래서 화면에만 `합산 3건` 칩을 두고, 누르면 개별 주문이 팝오버로 열리게 했습니다.

![합산 3건 칩을 누르면 개별 주문번호·주문일시·수량이 열린다 (샘플 데이터)](/assets/images/simple-event-winner/merge-popover.jpg)

### 4. 화면에 나오는 문장을 직접 정한 것

**이름 마스킹은 자릿수에 따라 다릅니다.** 2자는 `홍*`, 3자는 `홍*동`, 4자는 `홍**희`. 한국어 이름 대부분이 2~3자라 일괄 처리하면 발표 화면이 별표 밭이 됩니다.

**에러는 한국어 문장으로 던집니다.** `12행의 응모권 수량 값이 숫자가 아닙니다.` 오류를 만나면 곧장 엑셀을 고쳐야 하는 사람이 쓰는 도구이기 때문입니다.

**형식이 의심스러운 값은 막지 않고 알려만 줍니다.** 진짜 오류인지 예외 케이스인지는 운영자가 압니다. 도구가 판단할 일이 아닙니다.

### 5. 뽑는 순서와 보여주는 순서를 분리한 것

선정은 공정성의 영역이고, 나열은 가독성의 영역입니다. 그래서 선정이 끝난 뒤 표시 순서를 따로 정렬합니다. 기본은 발표명 가나다순이고, 마스킹 **전** 원본을 기준으로 삼습니다. 별표 처리된 문자열로 정렬하면 순서가 무의미해지니까요.

덕분에 나중에 "수량 많은 순으로 보여달라"는 요청이 왔을 때 선정 로직은 건드리지 않았습니다.

## AI가 한 것 / 내가 한 것

코드는 대부분 제가 직접 타이핑하지 않았습니다. 그런데도 시간이 짧게 들지는 않았고, 그 시간이 어디로 갔는지가 이 시리즈에서 제일 하고 싶은 이야기입니다.

**AI가 잘한 것.** 엑셀 파싱, 한·중 컬럼 alias 매칭, 국가별 전화번호 포맷, 시드 기반 셔플, 워크북 서식 생성. 명세가 명확한 순수 함수는 거의 한 번에 나왔습니다. 테스트까지 함께 써줘서 342개가 쌓였고, 덕분에 규칙이 자주 바뀌어도 겁내지 않고 고칠 수 있었습니다.

**넘길 수 없었던 것.** 위의 다섯 가지 판단입니다. 동점자 규칙을 통일하자는 결정은 AI가 먼저 제안하지 않았습니다. 요청한 대로 한국용 분기와 중국용 분기를 성실하게 만들어줬고, "이러면 합산된 사람은 어떻게 되지?"라고 물은 건 저였습니다.

AI는 **"어떻게 만들지"에 강하고, "무엇을 만들지 말지"에는 개입하지 않습니다.** 그래서 잘못된 요구사항도 그 어느 때보다 빠르게 구현됩니다. 디자이너의 일이 줄어든 게 아니라, 일의 비중이 옮겨간 쪽에 가깝습니다.

## 회고

### 잘된 점

- **백엔드를 안 만든 것.** 개인정보 송신 0건으로 규정 부담과 인프라 비용을 동시에 없앴습니다.
- **순수 함수 중심 설계.** 342개 테스트 덕분에 자주 바뀌는 정책을 자신 있게 고칠 수 있었습니다.
- **핸드오프 문서를 매 세션 남긴 것.** 다음 세션 진입 비용이 크게 줄었고, 이 글도 그 문서들에서 나왔습니다.

### 개선할 점

- `xlsx-js-style` 1.3MB+ 때문에 모바일 첫 로드가 느립니다. 동적 import로 분리 가능한데 아직 안 했습니다.
- 응모권명 한·중 자동 매칭이 없어서 매번 운영자가 드래그로 묶어야 합니다.
- UI 컴포넌트 통합 테스트가 없습니다. 순수 함수만 덮여 있습니다.
- 대표 주문번호를 단일 행의 최대 수량으로만 고릅니다. 한 주문이 여러 행으로 쪼개진 경우엔 주문 단위로 합산한 뒤 골라야 맞습니다.

### 마스킹 규칙

| 길이 | 결과 | 예 |
| --- | --- | --- |
| 0자 | `-` | — |
| 1자 | 원본 유지 | `김` |
| 2자 | 첫 + `*` | `홍*` |
| 3자 | 첫 + `*` + 끝 | `홍*동` |
| 4자 | 첫 + `**` + 끝 | `홍**희` |
| N (≥5) | 첫 + `*×(N-2)` + 끝 | `김***아` |

스프레드 연산자(`[...name]`)로 길이를 세어 이모지·결합문자도 1글자로 처리합니다.

## 작업 단계

**Phase 1 — 기초 도메인 함수.** Vite + React 19 + TS 스캐폴딩, `@makestar/design-system`을 `file:` 의존성으로 통합. CLAUDE.md 컨벤션을 먼저 못 박고 순수 함수부터 작성. macOS 엑셀의 NFD 문제를 파싱 단계 NFC 정규화로 일괄 해결.

**Phase 2 — 정규화 강화 (14 Fix).** 운영팀이 실제 파일을 올리며 나온 이슈 14건 정리. 국가번호 strip, 7자리 생년월일 보정, 27개 국가명 ISO 매핑, 국가별 전화 포맷. 테스트 130 → 261개.

**Phase 3 — 한·중 통합 파이프라인.** alias 확장, 동점자 규칙 일원화, `订单编号` 기반 멀티탭 join, 응모권 매핑 드래그 UI, 행 5종 분류. 테스트 316개.

**Phase 4 — 합산 내역 팝오버.** `createPortal`로 body 렌더(표 overflow 클리핑 회피), 트리거 좌표 기준 `fixed` 배치, 뷰포트 경계 클램프·세로 플립. 팝오버 내부 스크롤 시 닫히던 버그는 캡처 단계 리스너의 `e.target` 확인으로 해결. 테스트 320개.

**Phase 5 — i18n 4언어 + ZIP.** 헤더·뱃지를 KR/EN/ZH/JP로 분리, `WinnerImageCard`가 lang prop 수신, jszip으로 응모권 × 언어 전체 묶음. Windows Pretendard 로드 이슈 수정. 현재 v0.3.7, 테스트 342개.
