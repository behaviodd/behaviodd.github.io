## 왜 만들었나

제품에 쓸 아이콘이나 이모지가 필요할 때, 한 개를 그럴듯하게 만드는 건 이제 어렵지 않습니다. 문제는 **두 번째부터**입니다.

같은 프롬프트를 다시 넣어도 조명이 달라지고, 색 채도가 튀고, 어떤 건 외곽선이 생깁니다. 낱개로 보면 다 괜찮은데 나란히 놓으면 한 세트가 아닙니다. 이모지는 하나만 쓰는 물건이 아니라서, 세트로 안 보이면 쓸 수가 없습니다.

그래서 이 도구가 풀어야 할 문제는 "예쁜 이모지 만들기"가 아니라 **"같은 규칙을 매번 강제하기"** 였습니다.

---

## 무엇을 만들었나

**키워드 또는 이미지로 생성합니다.** 이미지를 첨부하면 그게 주 입력이 되고, 키워드는 선택입니다.

**스타일은 고정돼 있습니다.** 조명·색·구도·여백이 프롬프트에 사양으로 박혀 있어 매번 같은 규칙으로 나옵니다.

**참조 세트에서 골라 씁니다.** 라벨링된 200개 레퍼런스에서 검색해 최대 3개까지 합성해 넘깁니다.

**결과를 분류해 쌓습니다.** Good / Hold / Reject로 추리고, 어떤 프리셋과 어떤 프롬프트 버전에서 나왔는지 함께 남깁니다.

---

## 판단이 필요했던 순간들

### 1. API 키를 두 갈래로 라우팅한 것

생성 도구는 API 키가 필요합니다. 그런데 키를 어디에 두느냐에 따라 쓸 수 있는 사람이 달라집니다. 서버에 두면 사용자는 아무 준비 없이 쓸 수 있지만 서버가 있어야 하고, 브라우저에 두면 정적 호스팅으로도 배포되지만 사용자마다 키를 발급해야 합니다.

둘 다 두고 **자동으로 고르게** 했습니다. 서버가 키를 갖고 있으면 브라우저는 서버로 요청하고 서버가 키를 붙여 대신 호출합니다. 키는 브라우저로 내려가지 않습니다. 서버에 키가 없으면 설정에서 개인 키를 저장하고, 그 경우엔 브라우저가 구글을 직접 부릅니다. 개인 키는 서버를 거치지 않습니다.

중요한 건 이 구조의 한계를 문서에 적어둔 것입니다. **서버 내장 키는 사용자에게 안 보일 뿐, 그 서버에 접근할 수 있는 사람은 누구나 쓸 수 있습니다.** 공개 인터넷에 올릴 거면 인증과 사용량 제한이 따로 필요합니다. 감춘 것과 안전한 것은 다른데, 이 둘을 헷갈리면 나중에 청구서로 확인하게 됩니다.

### 2. 스타일을 취향이 아니라 사양으로 적은 것

"Fluent 3D 스타일로 만들어줘"는 지시가 아니라 기대입니다. 모델은 매번 다르게 해석합니다.

그래서 참조 세트 200장을 분석하고 A/B로 생성해 비교한 뒤, 결과를 **수치와 규칙으로 프롬프트에 고정**했습니다. 좌상단에서 오는 부드럽고 넓은 키 라이트, 위가 밝고 아래로 갈수록 진해지는 세로 그라디언트, 명도 0.82~0.92 · 채도 0.5~0.7의 밝은 캔디 톤에 주요 색 2~3개, 다만 금속·유리·흰색처럼 본래 중성인 재질은 원래 톤을 유지, 광택 소재에는 또렷한 흰 스페큘러 매트에는 은은한 셰인, 외곽선 없음, 정면에서 살짝 튼 3/4 시점, 1:1 캔버스에 피사체가 86~88%를 채우고, 흰 배경에 그림자 없음.

길지만 이게 요점입니다. "여백을 넉넉히" 같은 말은 뺐습니다. 모델이 알아서 해석할 여지를 남기면 그 여지만큼 결과가 흔들립니다.

### 3. 레퍼런스 200개를 직접 라벨링한 것

참조 이미지를 붙이면 결과가 좋아집니다. 문제는 어떤 참조를 붙일지 매번 사람이 찾아야 한다는 것입니다.

그래서 200개 레퍼런스에 **키워드·카테고리·형태·무드·색·표시 라벨**을 손으로 달았습니다. 이제 키워드를 넣으면 이 축들로 검색해 후보를 찾고, 최대 세 개를 캔버스에 합성해 참조로 넘깁니다. 파일명 검색으로는 "둥글고 말랑한 느낌"이나 "따뜻한 색 계열" 같은 조건을 걸 수 없습니다. 검색이 필요한 축을 미리 정해서 데이터에 심어두는 일 — 지루하지만 이 도구에서 가장 품이 든 부분이고, 결과 품질에 제일 크게 기여했습니다.

### 4. 참조와 복제 사이에 선을 그은 것

이미지를 첨부하면 그것을 그대로 흉내 내는 결과가 나올 수 있습니다. 남의 사진이나 브랜드 이미지를 넣으면 문제가 됩니다.

그래서 첨부 이미지를 바로 넘기지 않고 **두 단계로 처리**합니다. 먼저 분석해서 구조화된 설명만 뽑고, 그 설명을 생성 프롬프트에 붙입니다. 분석이 추출하는 것은 세 가지뿐입니다 — 대상의 형태와 범주, 대략의 포즈와 방향과 구도, 주요 색 팔레트. 그리고 사진의 디테일·배경·글자·로고·브랜드 마크는 따라 하지 말라고 명시합니다. 참조는 "이런 형태와 색"까지고, 그 너머는 복제입니다. 그 선을 도구가 대신 그어줍니다.

### 5. 특정 모델에 갇히지 않게 탈출구를 둔 것

메인 화면은 한 모델에 고정돼 있습니다. 선택지를 주면 조합마다 결과가 달라져서 비교가 무의미해지기 때문입니다.

대신 **모델에 종속되지 않는 프롬프트를 복사하는 경로**를 따로 뒀습니다. 그 프롬프트를 다른 모델 콘솔에 붙여 생성하고, 나온 이미지를 다시 업로드하면 같은 라이브러리에 같은 메타데이터로 쌓입니다. 도구가 기대는 모델은 언젠가 바뀌거나 없어집니다. 그때 라이브러리와 스타일 규칙까지 같이 버리게 되면 그동안 쌓은 게 사라집니다. 모델은 부품이고, 축적되는 건 규칙과 결과물이어야 합니다.

---

## AI가 한 것 / 내가 한 것

**AI가 잘한 것.** 하이브리드 키 라우팅, 두 단계 분석 파이프라인, 레퍼런스 검색과 캔버스 합성, 라이브러리 저장과 서버 동기화, 상태 필터, 설정 패널. 바닐라 HTML·CSS·JS로만 짰는데도 구조가 흐트러지지 않았습니다.

**넘길 수 없었던 것.** 렌더링 표준입니다. 명도 0.82~0.92라는 숫자는 모델이 알려주지 않습니다. 200장을 보고 "이 세트가 공유하는 게 뭐지"를 뽑아낸 다음, 그걸 모델이 알아들을 문장으로 번역하는 일입니다. 디자이너가 하던 스타일 가이드 작성과 정확히 같은 작업이고, 다만 독자가 사람에서 모델로 바뀌었습니다.

레퍼런스 라벨링도 그렇습니다. 어떤 축으로 검색할지를 정하는 건 이 도구를 무엇에 쓸지 아는 사람만 할 수 있습니다. AI에게 "라벨을 달아줘"라고 하면 달아주지만, 무엇을 축으로 삼을지는 먼저 정해줘야 합니다.

## 회고

### 잘된 점

- **프롬프트에 버전을 붙인 것.** 결과마다 어떤 버전에서 나왔는지 남아서, 규칙을 고칠 때 나아졌는지 나빠졌는지 셀 수 있습니다.
- **Good / Hold / Reject 큐레이션.** 생성은 확률이라 한 번에 안 나옵니다. 골라내는 과정 자체를 도구 안에 둔 게 맞았습니다.
- **키 라우팅의 한계를 문서에 적은 것.** 나중에 배포할 사람이 같은 함정을 밟지 않게 하는 가장 싼 방법이었습니다.

### 개선할 점

- 코드베이스가 둘로 갈라져 있습니다. 바닐라 앱과 React 프로토타입이 같은 기능을 각자 갖고 있어 한쪽만 고치기 쉽습니다.
- 배포가 내려가 있습니다. GitHub Pages로 올렸던 링크가 지금은 응답하지 않습니다.
- 디자인 시스템을 토큰만 맞춰 쓰고 있습니다. 바닐라라 컴포넌트를 가져올 수 없어서, 규칙은 지키되 구현은 복제입니다.
- 사용량 제한이 없습니다. 서버 키 모드로 공개하면 곧바로 문제가 됩니다.

| 항목 | 선택 | 이유 |
| --- | --- | --- |

| 서버 | Node (`server.js`) | 정적 서빙 + 키 프록시 + 라이브러리 동기화 |
| 생성 | Gemini (기본 `gemini-3.1-flash-image`) | 메인 UI는 단일 모델 고정 |
| 분석 | `GEMINI_ANALYSIS_MODEL` 또는 동일 모델 | 첨부 이미지 2단계 분석 |
| 저장 | `localStorage` + `data/history.json` | 브라우저 라이브러리 + 서버 동기화 |
| 디자인 | Makestar DS 토큰 정렬 | 컴포넌트 import 불가 → 토큰·규칙만 |

## 키 라우팅

```
브라우저 → /api/status
   │
   ├── geminiApiKeyLoaded: true
   │     → /api/generate 로 요청, 서버가 키를 붙여 Google 호출
   │       (키는 브라우저에 내려가지 않음)
   │
   └── false
         → 설정에 저장한 개인 키로 브라우저가 Google 직접 호출
           (키는 localStorage에만, 서버를 거치지 않음)
```

⚠️ 서버 내장 키는 **사용자에게 감춰질 뿐 서버에 접근 가능한 누구나 사용할 수 있습니다.** 공개 배포에는 인증과 사용량 제한이 별도로 필요합니다. 정적 호스팅(GitHub Pages)에서는 서버가 없으므로 개인 키 방식만 동작합니다.

## 렌더링 표준 `phase3-render-standard-v6-1`

레퍼런스 200장 분석 + A/B 생성 리뷰로 튜닝한 값입니다.

| 항목 | 규칙 |
| --- | --- |
| 조명 | 좌상단에서 오는 부드럽고 넓은 키 라이트 |
| 바디 | 위가 밝고 아래로 진해지는 세로 그라디언트 |
| 색 | 명도 ~0.82–0.92 · 채도 ~0.5–0.7 · 주요 색 2–3개 |
| 재질 예외 | 중성·금속·유리·흰색은 본래 톤 유지 |
| 스페큘러 | 광택 = 또렷한 흰 스팟 / 매트 = 은은한 셰인 |
| 외곽선 | 없음 |
| 시점 | 정면에서 살짝 튼 3/4 |
| 캔버스 | 1:1, 피사체가 86–88% (여백 6–10%) |
| 배경 | 흰색 단색, 드리운 그림자 없음 |

프롬프트 버전을 결과 메타데이터에 함께 저장해 버전 간 비교가 가능합니다.

## 레퍼런스 세트

Microsoft Fluent Emoji 3D PNG 200개. 매니페스트는 `assets/emoji/manifest.json`.

```json
{
  "id": "...",
  "label": "표시 라벨",
  "keywords": [...],
  "category": "...",
  "shape": "...",
  "mood": "...",
  "colors": [...],
  "src": "...", "sourcePath": "..."
}
```

매칭은 키워드 · 카테고리 · 형태 · 무드 · 색 · 표시 라벨을 함께 봅니다. 매칭된 자산은 최대 3개까지 캔버스에 합성해 참조로 넘깁니다. 라벨링 기준은 `docs/reference-labeling.md`.

## 첨부 이미지 2단계 분석

```
[1] 분석      추출: 형태·범주 / 포즈·방향·구도 / 주요 색 팔레트
              금지: 사진 디테일 · 배경 · 텍스트 · 로고 · 브랜드 마크 모사
       │
       ▼
[2] 생성      분석 결과를 최종 프롬프트에 덧붙여 생성
              결과는 흰 배경 · 그림자 없음 유지
```

첨부 원본 바이트는 저장하지 않습니다. 파일명 · MIME 타입 · 크기 같은 메타데이터만 남습니다.

## 라이브러리 · 큐레이션

결과마다 함께 저장하는 것: 키워드 · 이모지 타입 · 프로바이더/모델 · 생성 프롬프트 · 참조 자산 · 품질 프리셋(Simple / Cute / Icon / Reward) · 첨부 이미지 메타데이터 · 참조 분석 결과 · 미리보기 · 상태(`good` / `hold` / `reject`).

Good 개수를 세어 프리셋과 프롬프트 선택을 시간에 걸쳐 비교합니다.

## 수동 LLM 프롬프트 경로

```
키워드 입력 → 모델 비종속 프롬프트 복사 → 외부 모델 콘솔에서 생성
→ 이미지 다운로드 → [결과 업로드] 로 라이브러리에 편입
```
