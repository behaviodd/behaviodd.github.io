## 왜 만들었나

<!-- 확인 필요: 아래 첫 문단(도입 전 운영 방식)은 추정. 실제와 다르면 수정할 것 -->

인사평가는 원래 스프레드시트와 메일로 돌아갔습니다. 시즌마다 시트를 복제해 사람마다 탭을 만들고, 제출 여부를 눈으로 세고, 결과는 다시 잘라서 개별로 보냅니다.

문제는 마감 관리가 아니라 **한 번 새면 되돌릴 수 없다**는 쪽이었습니다. 인사 데이터는 잘못 보이는 순간 끝입니다. 공유 링크 하나, 탭 하나가 남의 평가를 열어줍니다.

그래서 "누가 무엇을 볼 수 있는가"를 사람의 주의력이 아니라 시스템이 정하게 만드는 것이 실제 목표가 됐습니다. 아래 다섯 가지 판단이 전부 그 한 문장에서 나옵니다.

---

## 무엇을 만들었나

**평가 주기를 한 번에 돌립니다.** 템플릿으로 문항을 구성해 주기를 발행하면 대상자와 평가자가 배정되고, 제출·승인 현황이 대시보드에 모입니다.

**세 종류의 리뷰를 같은 폼으로 받습니다.** 셀프·조직장·동료 리뷰가 같은 템플릿 엔진을 쓰고, 임시 저장으로 작성 중 유실을 막습니다.

**볼 수 있는 것만 내려갑니다.** 서버가 신원을 확인한 뒤 응답 자체를 행 단위로 걸러 보냅니다. 화면에서 숨기는 방식이 아닙니다.

**관리자가 직접 정리할 수 있습니다.** 조직 개편, 평가자 재지정, 잘못된 배정 정리를 관리 화면에서 처리하고 모든 변경은 감사 로그로 남습니다.

---

## 판단이 필요했던 순간들

### 1. 스프레드시트를 DB로 시작하고, 결국 갈아탄 것

처음 DB는 Google Sheets였습니다. 서버 비용이 0이고, 무엇보다 인사 담당자가 시트를 직접 열어 확인할 수 있다는 게 컸습니다. MVP 단계에서는 옳은 선택이었습니다.

수명이 끝난 건 정합성 때문입니다. 시트는 마지막에 쓴 사람이 이깁니다. 그래서 Supabase(관리형 Postgres)로 옮기되 **Auth는 쓰지 않았습니다.** 기존 Google SSO와 서버 세션은 그대로 두고 저장소만 갈아끼웠습니다. 인증까지 같이 바꾸면 문제가 터졌을 때 원인이 데이터인지 로그인인지 가릴 수 없어서입니다.

### 2. 소속을 이름이 아니라 ID 하나로 못 박은 것

팀 화면에서 구성원이 누락된다는 제보가 왔습니다. 파보니 **121명 전원의 소속 ID가 비어 있었습니다.** 중단된 마이그레이션의 잔재였는데, 이름으로 조직을 찾는 폴백 경로가 있어서 그때까지 화면은 멀쩡해 보였습니다.

이름 매칭을 더 똑똑하게 만들 수도 있었지만, 이름을 진실에서 빼는 쪽을 골랐습니다. **소속의 유일한 진실은 조직 ID이고 이름은 거기서 파생되는 표시값**입니다. 이름 매칭은 `B2B 사업팀`과 `B2B사업팀`, macOS의 자모 분리까지 감당해야 하는데 그건 규칙이 아니라 운입니다. 대신 ID가 비어 들어오면 런타임에 이름 경로로 한 번 해석해 채우고, 그래도 못 붙은 사람은 관측 목록에 남깁니다.

### 3. 필터를 만들어두고 켜지 않았던 것

행 단위 인가 필터는 이미 구현돼 있었습니다. 다만 스위치가 `shadow`였습니다. 로그만 남기고 실제로는 차단하지 않는 모드입니다. 과다 차단으로 정상 리뷰까지 숨겨지는 쪽이 무서워서 그렇게 뒀습니다.

그동안 서버는 **전사 평가 데이터를 로그인한 누구에게나 통째로 내려주고 있었습니다.** 신원 검증은 정상이었습니다. 신원대로 거르지 않았을 뿐이고, 화면에서만 안 보였습니다. 제보를 받고 중복 등록돼 있던 환경변수를 정리해 `enforce`로 켰습니다. 코드는 한 줄도 고치지 않았습니다. 남은 교훈은 하나입니다 — **"구현했다"와 "켜져 있다"는 다른 상태이고, 그 차이를 아는 방법은 로그뿐입니다.**

### 4. 비공개 문항의 경계를 화면이 아니라 답변 단위로 그은 것

조직장만 답하는 문항이 있습니다. 피평가자가 결과를 볼 때 이 답변은 보이면 안 됩니다. 흔한 구현은 해당 화면의 접근 권한을 막는 것입니다.

그렇게 하지 않고 **답변 하나 단위로 벗겨냈습니다.** 같은 데이터라도 누구의 경로로 열람하느냐에 따라 가려야 할 것이 다르기 때문입니다. 피평가자 경로로 들어올 때만 제거하고, 작성자인 조직장과 평가권자는 그대로 봅니다. 레이더 차트와 종합 점수에서도 같은 문항을 빼야 숫자로 역산되지 않습니다. 반대로 CSV 내보내기는 손대지 않았습니다. 반출 정책은 도구가 아니라 조직이 정할 문제라고 봤습니다.

### 5. 사람이 지정한 예외보다 조직도를 우선한 것

평가자는 두 갈래로 정해집니다. 관리자가 명시적으로 지정한 배정과, 조직도에서 파생되는 기본값입니다. 조직 개편 뒤 옛 배정이 남아 트리를 덮어썼고, 여러 사람이 이미 그 자리에 없는 리더에게 배정됐습니다.

우선순위를 다시 정했습니다. **명시 배정 → 조직 트리의 장 → 보고 대상** 순으로 내려가되, 개편 전에 시스템이 자동 생성한 배정은 예외가 아니라 잔재로 보고 정리했습니다. 사람이 의도적으로 지정한 예외는 트리보다 세지만, 과거의 자동 배정은 그렇지 않습니다. 정리한 8건은 백업과 감사 로그를 남기고 지웠습니다.

---

## AI가 한 것 / 내가 한 것

**AI가 잘한 것.** 재시도·백오프가 들어간 네트워크 유틸, 조직명 정규화, Sheets → Postgres ETL, 행 단위 필터 구현, 시트 진단 스크립트. 명세가 서면 구현은 빨랐고 테스트가 함께 나와서, 저장소를 통째로 갈아끼우는 동안 회귀를 잡아줬습니다.

**넘길 수 없었던 것.** 그 필터를 언제 켜느냐였습니다. `enforce`에는 과다 차단이라는 반대편 위험이 있고, 어느 쪽 위험을 감수할지는 "지금 이 조직에서 무엇이 더 무서운가"의 문제입니다. 비공개 문항을 CSV에서 뺄지도 같은 종류였습니다. 옛 배정 8건 중 무엇이 정리 대상이고 무엇이 살아 있는 예외인지는, 조직 개편을 아는 사람만 가릅니다.

하나 더 있습니다. 검증을 **하지 않기로** 한 것입니다. 개발 환경이 라이브 데이터베이스를 직접 보고 있어서 저장 경로를 브라우저로 확인하면 실제 인사 데이터에 흔적이 남습니다. 그래서 미검증으로 남기고 문서에 그렇게 적었습니다. AI는 "확인해보겠습니다"라고 답하지, 확인하지 않는 편이 낫다고는 말하지 않습니다.

## 회고

### 잘된 점

- **단계로 쪼갠 이전.** 이중 쓰기 → 읽기 전환 → 시트 제거로 나눠 각 단계에서 되돌릴 수 있게 했습니다.
- **인증을 건드리지 않은 것.** 저장소만 바꾸니 문제가 나도 원인 후보가 절반이었습니다.
- **핸드오프 문서 40개.** 위 다섯 가지 판단은 전부 그 문서에서 그대로 꺼냈습니다.

### 개선할 점

- `enforce`의 과다 차단을 아직 실사용으로 검증하지 못했습니다. 역할별 계정으로 훑어야 합니다.
- 비공개 문항 스트리핑도 관리자 계정으로는 경로를 타지 않아 실동작 확인이 남았습니다.
- 시스템 권한 그룹은 권한 변경이 조용히 버려지는데 화면은 "수정되었습니다"라고 답합니다. 거짓말하는 토스트가 제일 나쁩니다.
- 개발 환경이 라이브 데이터를 직접 봅니다. 테스트용 데이터셋 분리가 필요합니다.

## 아키텍처

```
[브라우저]  Google OAuth → 서버 세션 쿠키
     │      service_role 키·DB 접속 정보 없음
     ▼
[/api/*]  Vercel Functions
  auth        세션 검증 (쿠키 + Google 토큰 서명)
  authz       역할·권한 그룹 판정
  scope.ts    ★ 행 단위 인가 — filterSubmissions
                가시성 판정 / 익명 마스킹 / 비공개 문항 strip
  fromdb.ts   DB 행 → 도메인 타입 (소속은 orgUnitId만 내려감)
     │
     ▼
[Supabase Postgres]  RLS = 2차 방어선
```

행 단위 인가는 `SUBMISSION_SCOPE` 환경변수로 제어합니다. `shadow`는 판정 로그만 남기고 전량 반환, `enforce`는 실제로 거릅니다. 로그는 `[scope:read] {mode, uid, total, full, meta, hidden, masked, privateStripped}` 형태로 남아 과다 차단 여부를 사후에 셀 수 있습니다.

### 소속 판정 규칙

`users`에서 내려오는 소속 정보는 **`orgUnitId` 하나뿐**입니다. 주조직·부조직·팀 이름은 응답에 없고 조직 트리에서 파생합니다. `org_units.type`은 deprecated라 실데이터가 대부분 `'team'`이므로, 계층 분류는 type이 아니라 **부모 체인의 깊이**로만 합니다.

### 하향 평가권자 해석

```
명시 배정(reviewer_assignments)  →  조직 트리의 headId  →  보고 대상(manager)
```

자기 자신·비활성 계정은 후보에서 제외합니다. 개편 전 자동 생성된 배정(`created_by: system_migration_r1`)은 예외로 취급하지 않습니다.

## 이전 단계

**Phase 0 — 스키마.** Postgres 13개 테이블 DDL + RLS 작성. 이전 전 시트 정합성 진단(PK 중복·빈 셀·FK·JSON·NFC·이메일)을 돌려 전부 0으로 만들고, 고아 행 10건을 정리.

**Phase 1 — 이중 쓰기.** Sheets를 정본으로 두고 Postgres에 함께 기록. 두 저장소의 값이 갈리는지 관찰.

**Phase 2 — 읽기 전환.** 읽기를 Postgres로 옮김. 이 시점부터 소속이 `orgUnitId`로만 내려와, 이름에 의존하던 레거시 경로가 드러남.

**Phase 3 — 시트 제거.** Apps Script 웹앱 배포 해제, 클라이언트에 남아 있던 옛 스크립트 URL을 persist에서 폐기. 행 단위 인가 `enforce` 전환.
