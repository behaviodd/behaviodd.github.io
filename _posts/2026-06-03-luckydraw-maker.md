## 왜 만들었나

아이돌 이벤트 카페에는 럭키드로우가 거의 항상 있습니다. 상자에 포카나 특전을 넣어두고 손님이 하나 뽑는 방식입니다. 운영자는 무엇이 몇 개 남았는지를 직접 세어가며 굴려야 합니다.

이걸 웹으로 옮길 때 진짜 어려운 부분은 뽑기 화면이 아니었습니다. **상자에서 뽑는 감각을 어떻게 재현하느냐**였습니다. 상자는 한 번 꺼내면 그게 사라지지만, 코드로 짠 확률은 매번 독립 시행입니다. 확률이 정확해도 앞의 스무 명이 레어를 다 가져가는 일이 얼마든지 벌어지고, 그러면 뒷사람 입장에서 이건 고장 난 도구입니다.

그래서 이 프로젝트의 판단은 대부분 "확률이 맞는가"가 아니라 **"공정하다고 느껴지는가"** 쪽에 몰려 있습니다.

---

## 무엇을 만들었나

**만들고 공유하면 끝입니다.** 로그인해서 드로우를 만들고 아이템·수량·이미지를 넣은 뒤 URL을 공유하면 됩니다.

**손님은 가입하지 않습니다.** `/play/{id}` 링크나 QR로 들어와 바로 뽑습니다.

**재고가 실제로 줄어듭니다.** 당첨된 아이템은 남은 수량이 차감되고, 0이 되면 후보에서 빠집니다.

**두 가지 확률 모드가 있습니다.** 모두 같은 확률로 뽑거나, 수량에 비례해 희귀템이 덜 나오게 하거나.

---

## 판단이 필요했던 순간들

### 1. 확률 모델을 세 번 갈아엎은 것

처음엔 남은 수량에 비례해 뽑았습니다. 자연스러워 보였지만 **뽑을수록 확률이 계속 움직입니다.** 흔한 아이템이 소진될수록 레어의 확률이 올라가서, 늦게 온 손님이 유리해집니다.

두 번째 버전은 남은 수량이 아니라 **원래 수량 비례로 확률을 고정**했습니다. 이제 확률은 처음부터 끝까지 같습니다. 그런데도 불만이 남습니다. 독립 시행이라 100개 중 레어 5개가 앞쪽에 몰려 나오는 시퀀스가 얼마든지 나오니까요.

그래서 세 번째로 **부채(debt) 기반 추첨**으로 바꿨습니다. 매 뽑기마다 "이 아이템이 지금까지 자기 비율만큼 나왔는가"를 계산해서, 뒤처진 쪽에 가중치를 줍니다.

> `debt = (지금까지 뽑힌 횟수+1) × 자기비율 − 실제로 나온 횟수`

부채가 클수록 나올 확률이 높아지고, 결과적으로 각 아이템이 전체 시퀀스에 자기 비율대로 **균등한 간격**으로 흩어집니다. 상자에서 비복원으로 꺼내는 감각에 가장 가까운 모델이 이것이었습니다.

### 2. 추첨을 브라우저에서 하지 않기로 한 것

뽑기 결과를 클라이언트가 정하면 개발자 도구를 아는 사람이 원하는 것을 뽑을 수 있습니다. 굿즈에는 실제 금전 가치가 있고, 카페 이벤트에서 조작 의혹이 한 번 생기면 그걸로 끝입니다.

그래서 추첨은 전부 서버 API에서 일어납니다. 수량과 남은 개수는 브라우저에 아예 내려가지 않고, 차감은 데이터베이스 함수 안에서 당첨 기록과 함께 한 번에 처리됩니다. IP와 드로우 단위로 분당 30회 제한도 걸었습니다. **믿을 수 없는 곳에서 계산하지 않는다** — 규칙은 이 한 줄입니다.

### 3. 손님에게 로그인을 요구하지 않은 것

참여자 인증을 붙이면 중복 참여를 막을 수 있습니다. 하지만 카페 현장에서 줄 서 있는 손님에게 가입을 시키는 순간, 이 도구는 안 쓰이게 됩니다.

인증 대신 **노출 범위를 좁히는 쪽**을 택했습니다. 로그인하지 않은 사람에게는 활성 상태인 드로우만 보이고, 그마저도 남은 수량 같은 내부 값은 응답에 담기지 않습니다. 중복 참여는 기술이 아니라 현장 운영자가 눈으로 막는 문제라고 정리했습니다. 모든 것을 시스템으로 막으려 하면 정작 쓰이지 않는 시스템이 됩니다.

### 4. 한 앱에 디자인 언어를 두 개 둔 것

참여자 화면은 네오브루탈리즘입니다. 두꺼운 검정 테두리, 밀린 솔리드 그림자, 원색. 뽑기는 이벤트라 시끄러워야 합니다.

반면 운영자가 쓰는 생성·편집·보관함 화면은 조용한 업무 도구 스타일로 따로 뒀습니다. 재고를 세고 이미지를 올리는 화면에서 그림자가 튀고 색이 부딪히면 일이 안 됩니다. 두 언어는 `[data-admin]` 컨테이너를 경계로 갈리고, 배경 텍스처 오버레이도 이 안에서는 꺼집니다. **같은 앱이라고 같은 톤을 쓸 이유는 없습니다.** 보는 사람의 목적이 다르면 다른 화면입니다.

### 5. 옵션 추첨은 확률이 아니라 '가장 적게 나온 것'으로 정한 것

나중에 품목 아래 옵션 계층이 생겼습니다. "포카 1종"을 뽑으면 그 안에서 멤버가 갈리는 식입니다.

여기서는 확률을 쓰지 않았습니다. 가용한 옵션 중 **지금까지 가장 적게 지급된 것을 먼저** 주고, 동률일 때만 무작위로 가릅니다. 확률로 굴리면 특정 멤버만 계속 나오는 사고가 실제로 납니다. 품목은 "얼마나 희귀한가"의 문제지만 옵션은 "고르게 나갔는가"의 문제라, 같은 화면 안에서도 다른 규칙을 썼습니다.

## AI가 한 것 / 내가 한 것

**AI가 잘한 것.** 부채 기반 가중치 수식 구현, RLS 정책과 데이터베이스 함수, 이미지 WebP 자동 압축, 슬롯머신 셔플과 컨페티 연출, 마이그레이션 11개. 특히 확률 모델을 바꿀 때마다 따라오는 잔가지 — 소진 처리, 벌크 뽑기, 프리뷰 표시 — 를 빠짐없이 같이 고쳐준 게 컸습니다.

**넘길 수 없었던 것.** "공정한 뽑기"의 정의입니다. 세 번의 확률 모델은 전부 수학적으로 옳았고, 바뀐 건 무엇을 공정으로 볼 것인가였습니다. 매 시행의 확률이 같은 것인가, 전체 시퀀스의 분포가 고른 것인가. 후자를 골랐다는 건 이 도구가 "확률 계산기"가 아니라 "상자의 대체품"이라고 정의했다는 뜻입니다.

이런 건 요청하지 않으면 나오지 않습니다. AI에게 "확률대로 뽑아줘"라고 하면 정확히 그렇게 만들어주고, 앞쪽에 레어가 몰리는 시퀀스가 왜 문제인지는 말해주지 않습니다. 그 문제는 카페 앞에 줄이 서 있는 장면을 떠올려야 보입니다.

## 회고

### 잘된 점

- **서버 권위 추첨.** 결과를 정하는 코드가 한 군데뿐이라 확률 모델을 세 번 바꾸는 동안에도 손댈 곳이 하나였습니다.
- **부채 기반 분포.** "확률이 맞다"에서 "느낌이 맞다"로 목표를 옮긴 것이 이 프로젝트의 핵심입니다.
- **가입 없는 참여.** 링크와 QR만으로 끝나서 현장 도입 장벽이 없습니다.

### 개선할 점

- 클라이언트 쪽 추첨 코드가 아직 파일로 남아 있습니다. 어디서도 불리지 않는 죽은 코드인데, 남아 있다는 것 자체가 다음 사람에게 함정입니다. 지워야 합니다.
- 드로우를 수정하면 아이템을 지우고 다시 넣는 구조라, 옵션과 당첨 기록이 연쇄 삭제됩니다. 이벤트 도중 수정하면 기록이 날아갑니다.
- 참여자 중복 방지가 전적으로 현장 운영에 의존합니다. 의도한 선택이지만 대안(기기 단위 완충 정도)은 검토해볼 만합니다.

## 추첨 알고리즘

추첨은 `POST /api/draw/[id]/pick` 에서만 일어납니다. UUID 형식 검증 → IP+드로우 단위 레이트 리밋(분당 30회) → 드로우·아이템 조회 → 추첨 → 차감 순입니다. 한 번에 최대 10회까지 뽑을 수 있고, 반복 시 로컬 복사본에 차감을 반영해 같은 요청 안에서도 재고가 겹치지 않습니다.

**equal 모드** — 남은 수량이 1 이상인 아이템 중 균등 무작위.

**weighted 모드** — 부채 기반 stratified:

```js
const CONCENTRATION = 2;

const step     = totalQuantity - totalRemaining;      // 지금까지 뽑힌 횟수
const expected = ((step + 1) * quantity) / totalQuantity;  // 기대 누적 등장
const actual   = quantity - remaining;                // 실제 누적 등장
const debt     = expected - actual;                   // 양수일수록 "더 나와야 함"

weight = Math.pow(Math.max(0.001, debt), CONCENTRATION);
```

`CONCENTRATION`이 클수록 분포가 엄격하게 균등해집니다(1=완만, 2~3 권장). 음수 부채는 0으로 만들지 않고 `0.001`로 클램프해, 막판에 다른 후보가 모두 소진돼도 뽑힐 수 있게 남겨둡니다.

**차감** — `decrement_item_quantity` 함수(SECURITY DEFINER)가 아이템·옵션 수량 차감과 당첨 기록 삽입을 함께 처리합니다.

**옵션 선택** — 품목에 옵션이 있으면 확률이 아니라 지급 균등으로 고릅니다.

```sql
ORDER BY (o.quantity - o.remaining) ASC, random()
```
