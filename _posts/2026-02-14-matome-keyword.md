## 왜 만들었나

<!-- 확인 필요: 아래 두 문단(계기)은 기존 글에서 역으로 복원한 추정.
     이 프로젝트는 소스가 남아 있지 않아 당시 기록을 참고할 수 없었음 -->

특정 주제를 며칠씩 따라가야 할 때가 있습니다. 포털 뉴스 탭을 열어두고 새로고침하면 같은 사건을 다룬 기사 수십 개가 제목만 바꿔 쌓입니다. 정작 알고 싶은 건 "그래서 무슨 일이 있었나" 한 줄인데, 그걸 얻으려면 스무 개를 열어야 합니다.

요약 자체는 이제 어려운 기술이 아닙니다. 다만 요약 도구 대부분이 API 키를 요구하거나, 기사 링크를 하나씩 붙여넣게 합니다. **키워드만 넣으면 수집부터 요약까지 끝나는 것**이 목표였습니다.

---

## 무엇을 만들었나

**키워드만 넣으면 됩니다.** 쉼표로 구분해 여러 개를 넣을 수 있고, 날짜 범위도 지정합니다.

**세 군데서 동시에 모읍니다.** Google·Naver·Daum 뉴스를 RSS로 훑어 중복을 제거하고 최신순으로 정렬합니다.

**요약 방식을 고릅니다.** 기본은 API 키가 필요 없는 로컬 알고리즘, 더 자연스러운 문장이 필요하면 Gemini.

**실패해도 결과는 나옵니다.** 소스 하나가 죽어도 나머지로 답을 만들고, 무엇이 실패했는지 함께 알려줍니다.

---

## 판단이 필요했던 순간들

### 1. 기본값을 AI가 아니라 로컬 알고리즘으로 둔 것

Gemini를 기본으로 두면 요약 품질이 확실히 좋습니다. 대신 첫 화면에서 API 키를 요구하게 됩니다. 도구를 열자마자 키를 발급받으라는 안내를 만나면 대부분은 거기서 닫습니다.

그래서 기본값은 **LexRank**로 뒀습니다. 문장 간 유사도를 그래프로 만들어 중심 문장을 뽑는 고전적인 추출 요약이라, 외부 호출 없이 서버 안에서 끝납니다. Gemini는 "더 자연스러운 문장이 필요할 때 키를 넣는" 선택지로 내렸습니다. 품질 최상단을 포기하는 대신 **아무 준비 없이 열어도 결과가 나오는 상태**를 기본으로 만든 셈입니다.

### 2. 모델을 바꾸는 대신 입력을 닦은 것

처음 만든 요약은 형편없었습니다. "무단전재 및 재배포 금지" 같은 문장이 핵심 문장으로 뽑혀 나왔습니다.

추출 요약은 원문에 있는 문장을 그대로 골라옵니다. **입력에 쓰레기 문장이 있으면 요약에 쓰레기 문장이 나옵니다.** 알고리즘 잘못이 아니라 그게 원문에서 가장 자주 반복되는 문장이었을 뿐입니다. 그래서 모델을 손대는 대신 전처리에 매달렸습니다. HTML 태그와 엔티티, 기자명, 저작권 문구, 사진 캡션, 포털별 상용구까지 정규식 열여덟 개로 걷어냈습니다. 요약 품질은 이 단계에서 대부분 결정됐습니다.

### 3. 실패를 예외가 아니라 경고로 쌓은 것

뉴스 소스 세 곳 중 하나가 죽는 일은 자주 있습니다. 흔한 구현은 예외를 던져 요청 전체를 실패시키는 것입니다.

그렇게 하지 않고 실패를 `warnings` 배열에 **누적**했습니다. 살아남은 소스로 결과를 만들어 돌려주면서, 어디가 왜 실패했는지 함께 내려보냅니다. 뉴스 도구에서 "아무것도 못 봤다"와 "두 곳만 봤다"는 완전히 다른 상태입니다. 후자는 쓸모가 있고, 사용자는 그 사실을 알 자격이 있습니다.

### 4. 프레임워크를 쓰지 않은 것

화면은 입력 폼 하나와 결과 목록 하나가 전부입니다. React를 얹으면 빌드 파이프라인과 의존성 트리가 따라오는데, 이 UI가 그 대가를 치를 만큼 복잡하지 않았습니다. 단일 HTML 파일 518줄로 끝냈습니다.

대신 디자인은 사내 디자인 시스템과 맞췄습니다. 시스템의 `index.css`에서 시맨틱 토큰만 뽑아 CSS 변수 파일로 만드는 스크립트를 두고, 필요할 때 한 번 돌립니다. **패키지로 의존하지 않고 값만 복사해오는 방식**이라 빌드가 여전히 없고, 다크 모드도 변수 교체로 따라옵니다.

### 5. 서버리스가 서버가 아니라는 걸 배운 것

로컬에서 잘 돌던 요약이 배포하면 죽었습니다. 원인은 문장 분리에 쓰는 NLTK가 실행 시점에 데이터를 내려받으려 한 것이었습니다. 서버리스 함수의 파일 시스템은 읽기 전용이고, 쓸 수 있는 곳은 `/tmp`뿐입니다.

고친 방식은 단순합니다. 필요한 데이터를 저장소에 미리 넣어 함께 배포하고, `/tmp`를 대안 경로로 등록한 뒤, **세 군데를 순서대로 뒤져 먼저 찾은 것을 쓰게** 했습니다. 런타임에 무언가를 내려받는 코드는 서버리스에서 언젠가 터집니다. 필요한 건 배포에 포함시켜야 합니다.

## AI가 한 것 / 내가 한 것

**AI가 잘한 것.** RSS 파싱, 정규식 열여덟 개, sumy 연결, NLTK 경로 폴백, Pydantic 스키마, 그리고 프론트엔드 518줄 전부. 시리즈에서 가장 먼저 만든 프로젝트인데, 이때 이미 "명세가 명확하면 구현은 문제가 아니다"는 감각은 확실했습니다.

**넘길 수 없었던 것.** 기본값을 무엇으로 둘지였습니다. 품질이 좋은 쪽을 기본으로 하는 건 당연해 보이지만, 그러면 API 키가 없는 사람에게 이 도구는 존재하지 않는 것과 같습니다. 무엇을 기본으로 둘지는 **누구를 첫 화면의 주인으로 볼 것인가**의 문제고, 성능 비교표로는 답이 안 나옵니다.

요약이 형편없던 시절에 "모델을 바꿔볼까요"가 아니라 "입력이 더러운 것 아닌가"로 방향을 튼 것도 그렇습니다. 출력이 나쁠 때 모델을 의심하는 건 쉽고, 자기가 넣은 데이터를 의심하는 건 조금 덜 쉽습니다.

## 회고

### 잘된 점

- **로컬 우선 요약.** 준비물 없이 열자마자 쓸 수 있다는 것이 이 도구의 유일한 장점이자 가장 큰 장점입니다.
- **경고 누적.** 부분 실패를 정상 응답으로 다루는 구조가 실사용에서 가장 안정적이었습니다.
- **빌드 없는 프론트.** 정적 파일 그대로 배포되니 고칠 일이 생겨도 파일 하나만 열면 됩니다.

### 개선할 점

- 요약 결과를 캐시하지 않습니다. 같은 키워드를 다시 넣으면 매번 처음부터 다시 돌립니다.
- Gemini 사용량 관리가 허술합니다. 글자 수 하드 리밋 하나로 막고 있습니다.
- RSS에 의존하는 만큼 실시간성은 피드 갱신 주기를 못 넘습니다.
- 모바일에서 날짜 선택이 불편합니다.

### 프론트엔드

순수 HTML + JavaScript 단일 파일(518줄). 빌드 없음. Pretendard(CDN), `@makestar/design-system`에서 추출한 CSS 변수, Light/Dark 테마(localStorage 영속).

## 뉴스 수집

세 소스 모두 Google News RSS를 쓰되 쿼리로 갈라냅니다.

| 소스 | 탐색 방식 |
| --- | --- |
| Google News | 키워드 검색 |
| Naver News | `site:news.naver.com` 필터 |
| Daum News | `site:v.daum.net` 필터 |

한국어 설정은 `hl=ko&gl=KR&ceid=KR:ko`. 키워드 3개면 RSS 피드 9개를 파싱하고, URL 기준 중복 제거 → 날짜 범위 필터 → 최신순 정렬 → 상위 N건(최대 500)을 반환합니다.

## 요약 엔진

| 엔진 | 방식 | 특징 |
| --- | --- | --- |
| LexRank | 그래프 기반 문장 추출 | **기본값**, 키 불필요, 빠름 |
| LSA | 잠재 의미 분석 | 다른 관점의 핵심 문장 |
| Gemini | 생성형 요약 | 자연스러운 한국어, 키 필요 |

## 전처리

정규식 18개 이상으로 노이즈를 제거합니다 — HTML 태그·엔티티, 기자명, 저작권 표시, 사진 캡션, 포털별 상용구, 중복 공백·줄바꿈. 추출 요약은 원문 문장을 그대로 고르므로 이 단계가 결과 품질을 사실상 결정합니다.

## API

```
POST /api/search
  → keywords: ["AI", "반도체"]
  → date_from: "2026-02-01"
  → method: "lexrank"
  ← articles: [{title, link, source, ...}, ...]
  ← summary: "• 핵심 포인트 1\n• 핵심 포인트 2..."
  ← warnings: ["[Google News] RSS 피드 오류..."]
```

개별 피드 실패는 예외가 아니라 `warnings` 누적으로 처리해, 부분 성공을 정상 응답으로 돌려줍니다.

## 아키텍처

```
[입력]  키워드 · 날짜 · 요약 방식
   │
   ▼
[Frontend] index.html — 키워드 파싱 → POST /api/search
   │
   ▼
[FastAPI] api/index.py — Pydantic 검증 · 날짜 파싱
   │
   ▼
[core.fetch_news]
   키워드 × 소스(3) RSS 생성 → feedparser
   → HTML 정제 + 상용구 제거 → 날짜 필터
   → URL 중복 제거 → 최신순 정렬
   │
   ▼
[core.summarize_articles]
   LexRank / LSA → sumy 로컬 추출
   Gemini        → 한국어 뉴스 분석 프롬프트
   │
   ▼
[응답]  articles + summary + warnings
   │
   ▼
[렌더]  키워드 칩 · 요약 패널 · 뉴스 카드(소스 배지 · 태그 · 원문 링크)
```

## 서버리스 대응

NLTK `punkt_tab` 데이터를 런타임에 내려받으면 읽기 전용 파일 시스템에서 실패합니다. 해결:

1. 프로젝트에 데이터를 미리 번들해 함께 배포
2. `/tmp/nltk_data`를 대안 경로로 등록
3. 프로젝트 내 → `/tmp` → NLTK 기본 순으로 탐색해 먼저 찾은 것을 사용
